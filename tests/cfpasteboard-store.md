# CFPasteboard store

Build `cfpasteboard-store.c` against CoreFoundation (with the private header `CoreFoundation/CFPasteboard_Private.h`) and run it under Darling. It exercises the private CFPasteboard interface on unique boards: change counts, items and flavors in order, caller-chosen and allocated item identifiers, flavor flags (the Promised bit is the store's), ownership of a generation (writing without beginning one fails), replacing a flavor, new generations dropping everything, promises with a provider (called once, on first read or by `CFPasteboardResolveAllPromisedData`, with the all-provided, owner-changed and release callbacks), a provider that supplies nothing, size and name validation, the paste location, and promise visibility (a promise made with `kCFPasteboardFlavorPromiseVisible` reads as flagged Promised, one made without reads as made), and a host bridge (changes are reported, host replacements are not reported back, a lazily fetched flavor is requested on demand).

It uses only boards nobody else knows, so the result is the same when the boards live in the pboard service as when they live in the process. Prints `PASS` when every check holds.

Run with the argument `service` it first starts a board service inside the process (anonymous listener) and makes CoreFoundation use it, then also checks the service itself through a second client: the other client sees the board but may not write to it, a promise it reads is resolved by asking this process's provider, taking the board over notifies the previous owner, a promise of a client that disconnects is dropped, and malformed requests (missing or mistyped fields, over-long names, flags that do not fit) are refused without harming the service. It also checks the bridge with the service as the single store: a windowless client changes the general board and the (fake) bridge is told while the client is not told of its own change, a host import reaches other subscribers marked as an import and is not reported to the bridge, and a lazily imported flavor is read by the other client through the bridge's provider. This build needs `-I` of the CoreFoundation source directory for `CFPasteboardProtocol.h`. Cross-process behaviour over the real Mach service (a named board shared between two processes, a user's service not serving other users) is covered by `tests/src/pboard_service.c` in the darling repository.
